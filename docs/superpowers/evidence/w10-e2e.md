# Wave 10 evidence: end-to-end against the Stripe dev sandbox

Branch feat/billing. Server on port 3000 against `rootaroo_impl` (Docker MySQL 3307, Redis 6379), Stripe test mode,
`stripe listen --latest --events <billing events> --forward-to localhost:3000/api/v1/billing/webhooks/stripe/test`.
The `whsec`, the staff key (`ADMIN_BILLING_API_KEY`) and the settings below live only in gitignored `server/.env.impl`.

Harness: `server/scripts/e2e/harness.ts` (API client, seeding through register + household create, DB snapshots, evidence writer
that redacts keys, signing secrets, bearer tokens and Stripe-hosted URLs), `lifecycle.ts` (E5 to E15), `hosted.ts` (E1 to E4).
Lifecycle subscriptions are created in Stripe on test clocks (customer linked to the household through `billing_customers`,
`metadata {householdId, purchasedByUserId, env:'dev'}`), so webhook, worker and `upsertSubscription` run for real.

Settings: `BILLING_REQUIRE_TOS_CONSENT=false` (the sandbox has no Terms of Service URL yet, so the Checkout ToS checkbox
was not exercised), `BILLING_ENV_TAG=dev`, grace 7 days.

## Notes on how assertions were met

- E5: two households. Part A renews 2 days ago on the clock: `grace_until` equals the renewal invoice's `finalized_at` + 7 days
  and the household is allowed (reason `grace`). Part B renews 14 days ago, so grace has really elapsed in real time: blocked
  (402), then restored by a new card plus `invoices.pay`. Test clocks are started in the past for this; the entitlement check
  uses real time, so this is the only way to see "blocked after grace" without editing the database.
- E6: the seat change is paid immediately, `plan_change_version` goes 0, 1, 2, `rootaroo_hh7_year` is 12775.
- E7: with a failing card the change returns `pendingUpdate: true`, seats stay 5, a second change is refused with
  `PLAN_CHANGE_PENDING`; advancing the clock past `pending_update.expires_at` clears it and creates the
  `billing_plan_change_failed` notification. A second household shows seats moving to 6 only after the open invoice is paid.
- E9/E15 summary arithmetic is compared against the raw ledger over 2020 to 2031.
- E10: the staff alert goes through the mailer, which in dev logs `[DEV] ... admin alert not sent: [Billing] Dispute opened`;
  the scenario checks that log line (`E2E_SERVER_LOG`). The `payment` row can arrive after the `dispute` row (Stripe events
  are not ordered), so the scenario waits for it.
- E11: the listener is stopped, a subscription is paid, no local row exists (402), the listener is restarted and a manual
  reconcile creates the subscription and ledger rows; the run row is `succeeded`.
- E13: in a non-production server `resolveMode` is always `test`, so a test subscription does unlock a live-cohort household
  on this dev server. Isolation is shown with `resolveMode(..., 'production')` returning `live` and `computeEntitlement` for that
  mode seeing no `livemode=true` rows (blocked), plus the staff API in `mode=live` not listing the subscription.

## Findings (no server defects)

- Objects on a Stripe test clock are excluded from account-wide list calls (`subscriptions.list`, `invoices.list`). Reconciliation
  discovery of unknown subscriptions therefore cannot see test-clock subscriptions. This only affects the sandbox, not
  production, so E11 and E12 use real-time (clock-less) subscriptions. Everything else uses clocks.
- Harness-only fixes during the run: summary baseline taken before the payment (E9), out-of-order dispute/payment events (E10),
  a late creation webhook racing the planted drift (E12), Windows spawn of the `stripe` shim (E11). None needed a server change,
  so there are no failing-test or fix commits.
