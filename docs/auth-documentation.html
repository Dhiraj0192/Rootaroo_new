Overview

This covers the auth module of the Rootaroo server end to end: every endpoint, the exact code path a request takes, the tokens issued, and every database table the module touches — including columns and foreign-key relationships. Source: server/src/modules/auth/, server/src/shared/middleware/auth.ts, server/src/shared/middleware/socketAuth.ts, server/src/database/models/.

In plain terms "Auth" is short for authentication — it's the part of the app that answers two questions on every single request: "who are you?" and "are you allowed to do this?" It's the front door of the whole app: before anyone can see their household's chores, chat, or photos, they have to pass through this module first — sign up, log in, prove they own their email or phone number, and get handed a "key" (a token) that they show on every later request instead of typing their password again and again.

What the module does

  • Email + password registration and login, with bcrypt hashing (cost factor 12).
  • Google OAuth sign-in (authorization-code exchange + ID-token verification).
  • Phone OTP registration/login via Auth0 Passwordless SMS.
  • JWT access tokens (short-lived, stateless) + opaque refresh tokens (long-lived, stored in DB, rotated on every use).
  • Email verification and password reset, both via 6-digit codes emailed to the user.
  • Profile management: update profile fields, upload avatar (Cloudinary).
  • Account deletion: 30-day scheduled soft-delete, cancellable; plus immediate hard-delete for abandoned/unverified signups.
  • Socket.io authentication: the same JWT is used to authorize real-time WebSocket connections.

Request Lifecycle

Every auth HTTP request flows through the same layered pipeline. This is the shape to keep in your head before reading any individual endpoint below.

In plain terms Think of it like walking into a secured building. Router is the receptionist who reads the address you asked for and points you to the right department. Validate is security checking your paperwork is filled in correctly before you go further — wrong format, you get turned away immediately. Authenticate is the ID badge scanner — for anything sensitive, you need to prove who you are with your token before you're let in. Controller is the desk clerk who takes your request and passes it to the right specialist. Service is that specialist — this is where the actual work happens (checking passwords, talking to the database, sending emails). The Response is the clerk handing you back a result on your way out. Every single auth request — register, login, whatever — walks this exact same hallway.
Client

Sends an HTTP request to /api/auth/* (JSON body, optionally an Authorization: Bearer <accessToken> header).

Router

modules/auth/routes.ts maps the path + method to a handler chain.

Validate

validate(schema) middleware runs the request body through a Zod schema from validation.ts. Bad input is rejected here — the controller never sees it.

Authenticate

For protected routes only: authenticate middleware (shared/middleware/auth.ts) verifies the Bearer JWT and attaches the decoded payload to req.user. Missing/invalid/expired token → 401 before the controller runs.

Controller

controller.ts — thin. Pulls data off req, calls the matching service.ts function, wraps the result in { success: true, data }, or forwards thrown errors to next(e) for the global error handler.

Service

service.ts — all business logic and every Sequelize query lives here. Controllers never talk to models directly.

Response

JSON envelope back to the client: { success: true, data: ... } on success, or an error shape produced by the global error handler on failure.

Tokens & JWT

Rootaroo uses a classic two-token model: a short-lived stateless JWT for authorizing requests, and a long-lived opaque token stored server-side for getting new JWTs without re-entering credentials.

In plain terms Imagine a theme park. The access token is your wristband — it proves you paid and lets you walk into any ride without showing ID every time, but it expires after a few hours. The refresh token is the receipt in your pocket — you don't show it to every ride operator, but when your wristband expires you take it to the front gate and they print you a brand new wristband, no need to buy a ticket again. Every time you do that, the old receipt gets torn up and you get a new one — so if someone stole an old receipt from the trash, it's already useless. And the park only lets you hold 5 receipts at once — get a 6th, and the oldest one gets thrown out.

Access Token

JWT, stateless
  • Signed with env.jwt.accessSecret, expiry from env.jwt.accessExpiry (config-driven, not hardcoded).
  • Payload: { userId, email, role } — householdId is also read by the socket layer if present.
  • Never stored in the database — verified purely by signature + expiry on every request.
  • Checked by authenticate middleware for HTTP, and by socketAuthMiddleware for WebSocket connections.

Refresh Token

opaque UUID, stored in DB
  • Just a random UUID v4 string — not a JWT, carries no payload of its own.
  • Persisted in the refresh_tokens table, 30-day expiry.
  • Single-use rotation: every call to /auth/refresh deletes the old row and issues a brand-new refresh token + access token. A stolen/replayed old token simply fails once the legitimate client rotates it.
  • Capped at 5 per user: on issuance, if the user already has ≥5 refresh tokens, the oldest are deleted so at most 5 (roughly — the newest ones) remain.
  • Logout deletes the specific token row. Account deletion/cancel-pending wipes all refresh tokens for that user.

Endpoints

All routes are mounted under /auth. "Protected" requires a valid Authorization: Bearer header. "Optional-auth" endpoints work with or without a token — behavior branches on whether req.user is present.

In plain terms "Public" means anyone on the internet can call it with no login at all — makes sense, since you can't require a wristband to get the wristband. "Protected" means you must already be logged in and hand over your access token, or you get rejected before your request even reaches the real logic. "Optional" is the odd one out — it works both for someone half-way through signing up (no token yet) and for someone already logged in who just wants to add or change their phone number.

Workflow — Register

POST/auth/registerpublic

Body: { email, password, displayName? }

In plain terms Someone fills out the sign-up form. The server first checks nobody's already using that email. Then it never stores the actual password anywhere — it runs it through bcrypt, a one-way scrambler, and only saves the scrambled result. Even if the database leaked, nobody could read the real password back out of it. A new account row gets created, the person is immediately logged in (they get their wristband + receipt), and a 6-digit code is fired off to their email in the background so they can prove they actually own that address.
Validate

registerSchema: email must be valid format; password 8–128 chars; displayName optional (empty string treated as omitted, then defaulted).

Service

Look up User by lowercased email.

Exists → throw ConflictError (HTTP 409, "An account with this email already exists").

Service

bcrypt.hash(password, 12). displayName defaults to the email's local-part if not supplied.

Service

Create User row: role='member', isVerified=false.

Service

Issue an access token (JWT) and a refresh token (UUID, persisted to refresh_tokens, 30-day expiry, 5-token cap enforced).

Service

Auto-calls the email-verification flow: invalidates any stale unverified codes, generates a cryptographically secure 6-digit code (crypto.randomInt), stores it in email_verifications (15-min expiry), sends it by email.

If SMTP isn't configured (dev), the code is logged to console and returned in the response as verificationCode — dev convenience, not present when a real mailer is configured.

Response

201 → { user, tokens: { accessToken, refreshToken }, verificationCode? }

Full Screen-by-Screen Flow (Mobile Wizard)

The single /auth/register call above is only the first API hit of a much longer on-device journey. Source: mobile/src/screens/ChooseMethodScreen.jsx, SignUpScreen.jsx, SignupStep*.jsx, HouseholdSetupScreen.jsx, EmailVerificationScreen.jsx, InviteMembersScreen.jsx, shell shared/components/SignupWizardShell.jsx, state shared/store/signupProgress.js, routing shared/navigation/postAuthNavigation.js.

In plain terms Signing up isn't one form — it's a nine-screen wizard, and the moment the actual account row gets created in the database is different depending on how you started. Sign up with email, and the account exists the instant you tap "Continue" on the very first screen — everything after that (name, birthday, avatar, address) is just filling in a profile that already exists. Sign up with phone, and it's the opposite: nothing is created on the server at all until you've already picked a name, birthday, and avatar — the account and the phone number only get saved together, all at once, right before the OTP step. Whichever path you take, if you close the app halfway through, it remembers exactly which screen you were on and drops you right back there next time — the whole wizard's progress is saved on the device, not just held in memory.

Workflow — Refresh & Logout

POST/auth/refresh

Body: { refreshToken } — no Bearer header needed, the refresh token is the credential.

In plain terms Your wristband (access token) expired, so the app quietly hands over your receipt (refresh token) to get a new one — the user never notices, no re-login screen. The old receipt is torn up the instant the new one's issued, so it can only ever be used once. Logging out is simpler: just tear up that one device's receipt. Everything else (that device's login, other devices' logins) keeps working — logout only affects the device that asked for it.
Service

Look up RefreshToken row by token value, joined with its owning User.

Not found → 401 "Invalid refresh token".

Check

If expiresAt < now: delete the row and throw 401 "Refresh token expired — please log in again".

Rotate

Delete the old RefreshToken row, then generate a fresh access token + a brand-new refresh token (new row, new 30-day expiry). The old token can never be used again.

Response

200 → { accessToken, refreshToken }

Logout

POST/auth/logout

Body: { refreshToken }

Service

Delete the RefreshToken row matching that token value. Idempotent — no error if it's already gone.

Response

200 → { message: "Logged out successfully" }. Only this device's refresh token is revoked; other sessions are untouched.

Workflow — Google OAuth

POST/auth/googlepublic

Body: { code, redirectUri } — an OAuth authorization code from Google's consent screen on the client.

In plain terms User taps "Continue with Google," Google shows its own login screen (Rootaroo never sees the Google password), and hands back a one-time code. If an account with that email already exists, it just links Google onto it as an extra way to log in; otherwise it creates a brand new account. Workflow — Email Verification

In plain terms Two separate steps. First, the server generates a random 6-digit code and emails it — like any "confirm your email" flow you've seen elsewhere. Second, the user types that code back in, and if it matches (and hasn't expired after 15 minutes, and hasn't already been used) the account gets flagged as verified. This proves the person actually owns the email address they typed, not just that they typed an email address.

Workflow — Forgot / Reset Password

In plain terms "Forgot my password" screens are a favorite target for attackers trying to figure out who's registered on a service. That's why this endpoint always replies the same friendly "check your email" message whether or not the email exists — it just quietly does nothing if there's no account, instead of saying "no account found." If the account does exist, a one-time code goes to their inbox; typing it back in on the reset screen, along with a new password, swaps out the old password entirely.
POST/auth/forgot-passwordpublic

Body: { email }

Service

Find user by email.

Not found → return 200 silently anyway, same message either way — prevents attackers from using this endpoint to enumerate registered emails.

Service

Invalidate old unused reset codes for this user, generate a new 6-digit code, store in password_resets with 15-min expiry, email it (or dev-log).

POST/auth/reset-passwordpublic

Body: { code, password }

Service

Find a PasswordReset row by code where usedAt IS NULL and not expired.

This lookup is by code alone, not scoped to a specific email in the request — the code itself is the sole credential.

Home Screen — Widget Breakdown

Every card on the home screen, one at a time: what it shows, the exact logic that computes it, and which table + columns it's built from.

In plain terms The home screen looks like one screen, but under the hood it's really nine small independent calculations stitched together. Below, each widget gets its own mini-breakdown — what number or chart you see, in what order the server works it out, and exactly which spreadsheet (table) and which columns of it that number comes from.

1Tasks card

Shows: pending count · overdue count · completed today

Logic taskService.getTaskSummary(userId) loads every task in the household (no status filter at the query level), then loops through them in memory:
  • Status is completed and completed_at falls between today's start/end → completed today.
  • Not completed, has a due_date, and that date is before right now → overdue.
  • Everything else (not completed, not yet due, or due date is empty) → pending.
A task completed on an earlier day falls into none of the three buckets — it's already done and simply doesn't count toward today's numbers.
Tabletasks — reads household_id, status, due_date, completed_at.

2Groceries card

Shows: pending item count

Logic groceryService.getSummary(userId) loads all household grocery items, skips any that are archived, then counts everything with is_bought = false as pending. (The same function also computes a "bought today" figure for the grocery screen itself, but the dashboard only surfaces the pending count.)
Tablegrocery_items — reads household_id, is_bought, bought_at, archived_at.

3Todos card

Shows: pending count · completed today

Logic todoService.getSummary(userId) loads all household todo items and buckets each one: completed and completed_at is today → completed-today; otherwise → pending. Simpler than the tasks widget — todos don't have a separate "overdue" bucket on this summary.
Tabletodo_items — reads household_id, is_completed, completed_at.

4Expenses card

Shows: total expense count · total amount · your own net balance

Logic expenseService.getExpenseSummary(userId) loads every household member, every expense (with its participant splits), and every recorded settlement. For each member it tracks how much they paid versus their fair share across all expenses, then nets that against any settlements already recorded between members — a settlement actually reduces what's owed instead of just sitting as a separate history entry. The dashboard pulls the whole-household totals plus the caller's own entry from that per-user breakdown as "my balance." If this whole calculation throws (e.g. household has no expense data configured yet), the dashboard silently falls back to zeros rather than failing the entire home screen load.
Tablesexpenses (paid_by, amount, split_type), expense_participants, settlements, household_members.

5Notifications badge

Shows: unread count

Logic A single count query — notification_history rows for this user where is_read = false. No date window, no household scoping needed (already scoped to the user).
Tablenotification_history — reads user_id, is_read.

67-day activity chart

Shows: for each of the last 7 days — tasks completed, todos completed, groceries bought, and whether the household "stayed engaged" that day

Logic loadCompletions pulls every completed task, completed todo, and bought grocery item from a rolling 60-day window (shared with the streak calculation below), and buckets each one into a per-day tally using the household's own timezone — not the server's — so a completion at 11:58pm local time lands on the right calendar day. Separately, loadEngagementDays checks the same 60-day window for any chat message, ping/check-in, feed post, or calendar event on a given day. The chart then shows the last 7 days of that daily tally, and marks a day "engaged" if it had a chore completion or one of those other signals — so a day the family just chatted still lights up, even with zero chores done.
Tables tasks (completed_at, completed_by, points), todo_items (completed_at, assigned_to), grocery_items (bought_at, bought_by) — plus engagement-only signal from chat_messages, ping_requests, check_ins, feed_posts, calendar_events (each just checked for created_at/checked_in_at falling on that day).

7Streak

Shows: current consecutive-day streak · all-time best streak

Logic Reuses the exact same daily "did anything happen" data as the activity chart, just over the full 60-day window instead of 7. Best scans oldest→newest looking for the longest unbroken run of engaged days. Current scans backwards from today and stops counting the moment it hits a day with nothing — chore or otherwise. Because it shares the exact same day-by-day truth as the activity chart, the streak number never contradicts what the chart's dots are showing.
TablesSame as the activity chart above.

8Leaderboard

Shows: household members ranked by points earned this week

Logic Built from the same completions data, but only the current 7-day window (not the full 60-day streak window), and only real chore completions — chat/pings/etc. don't earn points here. A completed task adds its own points value (defaults to 1 if unset); a completed todo or bought grocery item always adds 1. Points are credited to whoever did the work (completed_by / assigned_to / bought_by), summed per member, and every household member is listed even at zero points — sorted highest first.
Tableshousehold_members, users (for name/avatar), tasks (points), todo_items, grocery_items.

9Recent activity feed

Shows: the last 8 chore completions across the household, newest first, with who did it and how many points

Logic Same weekly completions list that feeds the leaderboard — every individual task/todo/grocery completion this week is kept as its own event (not just summed per person), sorted by time descending, and trimmed to the 8 most recent. Each entry is enriched with the acting member's display name and avatar for the feed.
TablesSame as the leaderboard above.

Feed Feature — Overview

A household-scoped social feed: text/photo/video posts, likes, threaded comments with emoji reactions, and person-tagging. Source: server/src/modules/feed/, mobile src/screens/FeedScreen.jsx.

In plain terms Think of a mini Instagram/Facebook feed, but scoped tightly to just your household — nobody outside the family group can ever see a post. People share text updates, photos, or videos; others can like them, comment, reply to a specific comment, and react to comments with emoji. New posts show up for everyone in the household almost instantly through a live connection, on top of a regular push notification.

Key behaviors

  • Every read/write is scoped to the caller's own household — there is no cross-household visibility.
  • Comments thread one level deep: a reply to a reply is re-attached to the original root comment, not nested infinitely.
  • Comment reactions are a fixed emoji set: 👍 ❤️ 😂 😮 😢 🙏.
  • Posting broadcasts a WebSocket event (feed:new-post) to the household's room, plus a push notification to every other member — both fire-and-forget, so a failure there never blocks the post itself.
  • Feed listing supports both classic "load older" pagination (cursor) and a lightweight polling mode (since) for catching up on new posts.
  • Deleting a post or comment is allowed for its owner, or any household admin; deleting a comment is also allowed for the post's own owner (moderating their own post).

Vault Feature — Overview & Screens

A zero-knowledge, end-to-end encrypted document store — photos and PDFs (passports, IDs, insurance papers) encrypted on the device before they ever leave it. Source: server/src/modules/vault/, crypto core mobile/src/shared/crypto/vaultCrypto.js + vaultSetup.js + secureKeyStore.js + keyPinStore.js, screens VaultSetupScreen.jsx, VaultUploadScreen.jsx, VaultViewerScreen.jsx, VaultListScreen.jsx.

In plain terms Every other feature in this app trusts the server with plain, readable data. The vault deliberately does not. It's built on the assumption that the server itself might be hostile — hacked, subpoenaed, or just plain nosy — and designs around that instead of around it being trustworthy. Files are scrambled into unreadable ciphertext right there on the phone, using a key the server is mathematically never given, before a single byte is uploaded. This is the same category of design as Signal or WhatsApp's encrypted backups, applied to a household's important documents — passport scans, insurance cards, ID photos.

Screens

  • VaultSetupScreen.jsx — first-time setup: generates the user's personal encryption key pair, asks whether to enable passphrase-based recovery or go fully zero-knowledge (no recovery at all).
  • VaultUploadScreen.jsx — pick a file, encrypt it on-device, upload the ciphertext. Also lazily runs key setup here if the user skipped it earlier.
  • VaultListScreen.jsx — the document list, storage usage indicator.
  • VaultViewerScreen.jsx — downloads ciphertext, decrypts it in-memory, and displays it — the decrypted bytes are never written to disk.

The headline guarantee

The server only ever stores and transmits ciphertext and public keys. It never sees a plaintext document, a plaintext AES key, or a usable private key — even if the entire database and file storage were leaked, an attacker holding just that leak could not read a single document. This is what "zero-knowledge" means here: not that the server promises not to look, but that it has literally nothing readable to look at.

Crypto Primitives

All cryptography runs client-side via the WebCrypto API (globalThis.crypto.subtle), backed by native crypto on-device. Source: mobile/src/shared/crypto/vaultCrypto.js.

In plain terms Three different cryptographic tools, each doing a different job, combined into what's called "hybrid encryption" — the same overall pattern HTTPS itself uses. One tool is fast and encrypts the actual file. A second, slower tool doesn't encrypt the file at all — it only encrypts the key to the first tool, once per person who's allowed to open the file. A third tool turns a human passphrase into something strong enough to be a real encryption key, used only for the optional "back up my key" safety net.

1AES-256-GCM — the file cipher

Actually encrypts the document itself

WhatA 256-bit symmetric key, generated fresh for every single document (generateAesKey). "Symmetric" means the same key both locks and unlocks the file.
HowencryptFile/encryptBuffer generate a brand-new random 12-byte IV (initialization vector — never reused, never predictable) for every encryption, then run AES-GCM, which produces ciphertext plus a 128-bit authentication tag. That tag is what makes decryption fail loudly if even one byte of the ciphertext was tampered with or corrupted, instead of silently returning garbage.
Why per-documentA fresh key per file means one compromised document key never exposes any other document — no blast radius beyond the single file it belongs to.

2RSA-OAEP-4096 — the key wrapper

Protects the AES key itself, once per person who needs access

WhatA 4096-bit RSA key pair per user (not per document) — a public key and a private key. The public key can be handed to anyone; the private key never leaves the device it was generated on.
HowwrapKey encrypts (“wraps”) a document's AES key using a specific person's RSA public key — only that person's matching private key can reverse it (unwrapKey). This is why a document with 4 household members who can see it ends up with 4 separate wrapped-key rows (one per person) in vault_document_keys — the file itself is encrypted only once, but its key is individually re-locked for each authorized viewer.
Why not just RSA the whole fileRSA is slow and has strict size limits — it's built to encrypt small things like keys, not multi-megabyte files. AES does the heavy lifting; RSA only ever touches the tiny 256-bit key.

3PBKDF2-SHA256 — passphrase stretching

Turns a human-memorable passphrase into a real encryption key, for backup only

What800,000 iterations of PBKDF2 with a fresh random 32-byte salt per user. Used only if the user opts into passphrase-based recovery — never touched at all in zero-knowledge mode.
Why so many iterationsA passphrase typed by a human is far weaker than a real 256-bit key. Running it through 800,000 rounds of hashing deliberately makes each guess slow, so an attacker who steals the encrypted backup can't just brute-force every dictionary word in seconds — each attempt costs real, deliberate time.
What it protectsThe derived key encrypts the user's RSA private key (not any document) before that encrypted blob is optionally uploaded to the server as a recovery backup. The salt itself isn't secret — it's stored right alongside the ciphertext, which is standard practice; secrecy comes from the passphrase, not the salt.

Randomness rule

Every IV and every salt in this system comes from crypto.getRandomValues — a cryptographically secure random source. Never a counter, never a timestamp, never anything predictable. Reusing an IV with AES-GCM is a well-known way to catastrophically break the encryption; the code takes explicit care to generate a fresh one on every single encrypt call.

Workflow — Key Setup ("Key Ceremony")

Runs once per user, the first time they touch the vault (either explicitly via VaultSetupScreen, or lazily on first upload). Source: mobile/src/shared/crypto/vaultSetup.js → setupVaultKeys.

In plain terms This is the one-time "create your vault identity" step — like generating your own personal lock-and-key pair that only you control. The private half gets tucked into your phone's actual secure hardware (the same chip that protects Face ID/fingerprint data), so even a compromised app can't casually read it back out — unlocking it requires a real biometric or PIN prompt every time. Then you're asked a real security tradeoff: back up your key behind a passphrase you choose (so losing your phone doesn't mean losing your documents), or skip that entirely for maximum security at the cost of "lose the phone, lose the vault, forever."
Client

Generate a fresh RSA-OAEP-4096 key pair on-device via WebCrypto.

Client

Export the public key as base64 SPKI (safe to share) and the private key as a JWK (needed so it can be written into the hardware keychain).

Client

storePrivateKey writes the private key JWK into expo-secure-store with requireAuthentication: true — from this point on, every future read of this key triggers a real OS-level biometric/PIN prompt (Secure Enclave on iOS, TEE/StrongBox on Android). This isn't a JavaScript popup that could be bypassed — it's enforced by the phone's own hardware.

Branch — backup

If the user chose passphrase backup: derive an AES key from their passphrase via PBKDF2 (800K iterations, fresh salt), encrypt the private-key JWK with it, and hold onto the resulting ciphertext blob.

Branch — zero-knowledge

If the user chose "no backup": skip the step above entirely. Nothing derived, nothing encrypted, nothing sent — this is a deliberate no-op, not a stub.

Server

POST /vault/keys/me — the server receives the public key (not secret) and either the encrypted backup blob, or the literal string 'none' if zero-knowledge mode was chosen. VaultKey.upsert stores it keyed by userId.

Client — TOFU

verifyPublicKey pins this freshly-generated public key locally as "trusted" for this user — Trust On First Use. Every future time this user's public key is fetched from the server, it gets compared byte-for-byte against this pin.

Workflow — Upload Document

Endpoint: POST /vault/, multipart, max 20MB, images and PDFs only.

In plain terms By the time the file reaches the server, it's already unreadable gibberish — the server's only job is to store those bytes and remember who they belong to. All the actual security work (scrambling the file, protecting its key) happens before the network request is even made.
Client

Generate a brand-new AES-256-GCM key, unique to this one document.

Client

encryptFile encrypts the file's raw bytes with that key and a fresh random IV, producing ciphertext + IV + a 128-bit auth tag.

Client

Wrap the document's AES key with the uploader's own RSA public key (wrapKey) — this is the "I can open the file I just uploaded" key.

Server

The encrypted file bytes (ciphertext) are uploaded to POST /vault/. The server relays them straight to Cloudinary as an opaque raw resource — it never attempts to interpret them as an image or PDF, because to the server they're indistinguishable from random noise.

Service

Storage quota check first: sums this user's existing sizeBytes across all their documents, rejects with 403 if adding this file would exceed 2GB.

Service

Inside one transaction: create the VaultDocument row (storing the Cloudinary reference, the wrapped AES key as encrypted_key, and the IV — all opaque to the server), and create a matching VaultDocumentKey row that's specifically the uploader's own wrapped copy of that same key.

Response

201 → document metadata + the Cloudinary download URL for the ciphertext + the IV (needed later to decrypt).

Current scope: private, not yet shared

Every list/read/key-fetch query in vault/service.ts filters by uploadedBy: userId — right now a document is only ever visible to the person who uploaded it, even though it belongs to their household. The VaultDocumentKey table's whole design (one wrapped-key row per authorized viewer) exists specifically to support sharing a document with other household members via a future "key ceremony" (re-wrapping the AES key for each additional person's public key) — but as the code stands today, that re-wrapping step for other users isn't wired into any endpoint yet. Worth knowing if the product goal is "shared family vault" vs. what's actually live right now.

Workflow — View / Decrypt Document

In plain terms Opening a document runs the upload process in reverse: get the scrambled file down from the server, unlock the one key that can unscramble it (which itself requires a biometric prompt), then decrypt — all in the phone's memory. The unscrambled version is never saved to the device's storage, so there's no leftover plaintext file sitting in a downloads folder after you close the viewer.
Server

GET /vault/:id returns the document's metadata, the Cloudinary ciphertext URL, and the IV. GET /vault/:id/key separately returns this user's personally wrapped AES key for that document (from vault_document_keys).

Client

Download the ciphertext bytes from the Cloudinary URL.

Client

getPrivateKey pulls the user's RSA private key out of the hardware keychain — this is the moment the OS biometric/PIN prompt actually fires. A missing key here is distinguished from a failed authentication: "never set up on this device" returns null, a cancelled/failed biometric check throws instead, so the app never confuses the two.

Client

unwrapKey uses that private key to unwrap this document's AES key. The result is a non-extractable in-memory key — even the app's own JavaScript can't pull its raw bytes back out once unwrapped, only use it for decryption.

Client

decryptFile runs AES-GCM decryption using the unwrapped key, the stored IV, and the auth tag. If the ciphertext was tampered with, or the wrong key/IV is used, this throws immediately rather than silently returning corrupted data.

Client

The plaintext bytes are held only in memory for display and are explicitly never written to disk.

Workflow — Passphrase Backup & Recovery

Only relevant if the user chose passphrase backup during key setup. Zero-knowledge users have no recovery path by design.

In plain terms This is the safety net for "I got a new phone" or "I reinstalled the app." Instead of storing your private key in the clear anywhere, the app stores an encrypted copy of it — locked behind a passphrase only you know. On a new device, you type that passphrase back in, the app tries to unlock the backup with it, and either it works (correct passphrase) or fails hard (wrong passphrase) — there's no partial credit, no silent fallback.
Backup (at setup)

The private key JWK is encrypted with a PBKDF2-derived key from the chosen passphrase, and the resulting blob — { ciphertext, iv, authTag, salt }, all self-contained — is what gets uploaded as privateKeyEncrypted in POST /vault/keys/me. Storing the salt inside the blob itself means recovery works purely from the server copy, with no dependency on anything cached locally on the original device.

Recovery (new device)

GET /vault/keys/me fetches the stored public key + encrypted backup blob.

Client

User enters their passphrase. decryptPrivateKeyFromBackup pulls the salt out of the blob, re-derives the same AES key via PBKDF2, and attempts to decrypt.

Outcome

Wrong passphrase → the AES-GCM auth tag check fails and throws a hard error, deliberately with no retry-with-different-logic fallback. Correct passphrase → the recovered private key JWK is re-imported and re-stored into this new device's hardware keychain, and normal vault access resumes.

Security Model & Threat Handling

In plain terms Most features in this app assume the server is trustworthy and just build guardrails around user mistakes. The vault assumes the opposite — that the server itself could be the attacker — and every design decision below is a direct answer to a specific way a hostile or compromised server could try to cheat.

!Threat: server swaps someone's public key mid-exchange

RiskIf the server could hand out a public key it controls instead of the real recipient's, it could trick the app into wrapping a document's AES key for the attacker's key instead of the intended person's — a classic man-in-the-middle on the key exchange itself.
DefenseTOFU public-key pinning (keyPinStore.js). The very first time a user's public key is seen, it's pinned locally. Every later fetch of that same user's key is compared byte-for-byte against the pin — a mismatch returns 'changed' and the operation is blocked, never silently allowed. Updating a pin after a real key change requires explicit user confirmation, never happens automatically.
Known gapThe documentation in the code is explicit about this: the very first key fetch for someone has no prior pin to check against (the same limitation SSH's "trust this host key?" prompt has on day one). A future fingerprint-display step is the planned fix — this isn't hidden, it's called out directly in the source comments.

!Threat: stolen device / stolen database

DefenseThe private key lives only in hardware-backed secure storage, gated by a real biometric/PIN prompt at the OS level — not a software check the app could be tricked into skipping. Someone with the phone unlocked can access documents; someone with just a copy of the app's storage or the server database cannot.

!Threat: weak passphrase brute-forced from a leaked backup

Defense800,000 rounds of PBKDF2 make each individual guess deliberately expensive — a tradeoff explicitly favoring security over speed, and only ever exposed to this risk at all if the user opted into backup mode in the first place.

!Threat: tampered ciphertext

DefenseAES-GCM's built-in authentication tag makes any bit-flip in the stored ciphertext detectable — decryption throws instead of returning corrupted or attacker-manipulated plaintext.

Expense & Bills Feature — Overview & Screens

Shared household spending — who paid, who owes what, and a "who pays whom" plan that minimizes the number of actual payments needed to settle everyone up. Source: server/src/modules/expense/, mobile ExpenseListScreen.jsx, ExpenseDetailScreen.jsx, CreateExpenseScreen.jsx, ExpenseLedgerScreen.jsx, ExpenseSettlementScreen.jsx, MemberBalanceDetailScreen.jsx.

In plain terms This is Splitwise, built into the household app. One person pays for groceries, the bill gets split — evenly or in custom amounts — across whoever it applies to, and the app keeps a running tally of who owes whom. The cleverest part isn't tracking the debts (that's simple bookkeeping) — it's turning a tangle of "Alice owes Bob $20, Bob owes Carol $15, Carol owes Alice $5" into the smallest possible number of actual payments that settles everyone up.

Screens

  • ExpenseListScreen.jsx — every expense logged, newest first.
  • CreateExpenseScreen.jsx — log a new expense: title, amount, who paid, who it's split between, equal or custom split.
  • ExpenseDetailScreen.jsx — one expense's full breakdown: each participant's share and settled status, plus edit/delete/remind/settle actions.
  • ExpenseLedgerScreen.jsx — the simplified "who pays whom" plan for the whole household.
  • MemberBalanceDetailScreen.jsx — one specific relationship: exactly how much you and one other member owe each other.
  • ExpenseSettlementScreen.jsx — record a real-world payment (cash, Venmo, etc.) between two members.

Key rules

  • Only an expense's creator (the payer) or an admin can edit, delete, remind, or mark it settled.
  • Every participant (and the payer) must actually belong to the household — verified on every create/update.
  • Recording a settlement is restricted to the person paying (fromUserId must match the caller) — you can log that you paid someone, not that someone paid you.
  • Money math is done carefully: shares are rounded to the cent, with any leftover penny from an equal split assigned to the payer, and custom splits are validated to sum to the exact expense amount before anything is saved.

Workflow — Create & Split an Expense

POST/expenses/

In plain terms Two ways to split a bill: evenly, where the app does the division for you (and quietly absorbs any odd penny so the numbers add up exactly), or custom, where you type in exactly what each person owes and the app double-checks your numbers actually add up to the total before accepting it. Either way, nothing is a "guess" — every participant ends up with an exact cent amount, verified against the total.
Guard

Both the payer and every listed participant must actually be members of the caller's household — checked against household_members, not just trusted from the request.

Split — equal

calculateShares: divide the amount evenly, round each share to the cent. Because rounding can leave a stray penny unaccounted for (e.g. $10 ÷ 3 = $3.33 × 3 = $9.99, one cent short), that exact remainder is added onto the payer's own share — so the shares always sum to the real total to the cent, and the person who fronted the money absorbs the rounding, not some arbitrary participant.

Split — custom

Use the caller-supplied share amounts as-is, but validate first: no negative shares allowed, and the shares must sum to the expense's total amount (within a one-cent tolerance for floating-point safety). Off by more than a cent → rejected outright, nothing saved.

Service

Create the Expense row, then bulk-insert one ExpenseParticipant row per person with their exact share, is_settled: false.

Workflow — Balances, Ledger & Debt Simplification

GET/expenses/summary
In plain terms This is the clever part of the whole feature. Imagine three roommates: Alice paid for groceries and is owed money, Bob paid for nothing and owes everyone, Carol is in between. Naively, you'd end up with a tangled mess of individual IOUs — "Bob owes Alice $10 for groceries, Bob owes Carol $5 for gas, Carol owes Alice $3 for takeout"... The app doesn't show you that mess. It steps back, works out each person's single overall balance (are they, net, owed money or do they owe money — and how much), and then works out the fewest possible payments that would zero everyone out. Often that's genuinely fewer transactions than the raw list of expenses would suggest — Bob might just pay Alice once, instead of paying Alice and Carol separately.
Step 1 — raw totals

For every household member, tally two numbers across every expense ever logged: how much they paid in total, and how much their share of all expenses adds up to.

Step 2 — settlement adjustment

Every recorded Settlement (a real payment someone already made) shifts these numbers: the payer's balance moves up (they paid down debt), the receiver's balance moves down (their claim was paid off) — so a settlement isn't just a history entry, it actually changes what's currently owed.

Step 3 — net balance

Each person's final number is paid − share + settlement adjustment. Positive means the household owes them; negative means they owe the household.

Step 4 — simplify

computeSimplifiedLedger: split members into creditors (net positive, sorted biggest-owed-first) and debtors (net negative, sorted biggest-owed-first). Repeatedly match the biggest creditor against the biggest debtor, generate one payment for whichever amount is smaller, reduce both balances by that amount, and move on to the next pair once someone hits zero. This is a standard greedy debt-simplification algorithm — it doesn't guarantee the mathematically fewest possible transactions in every edge case, but it gets very close with a simple, fast approach.

Response

{ netBalances, totalExpenses, totalAmount, ledger } — the ledger is the actual "X pays Y $Z" action list the Ledger screen shows.

GET/expenses/pairwise/:userId
Service

A different, more direct calculation than the ledger — this one deliberately skips the simplification/rerouting step. For the target member, it walks every expense and every settlement and tracks debt specifically between that person and each other individual member, so it can answer "exactly how much do you and Bob owe each other," even if the simplified household-wide ledger routes their debt through a third person instead.

Creating a household, inviting/joining, managing members and roles, and the household's own 30-day-grace deletion flow. Source: server/src/modules/household/, mobile HouseholdSetupScreen.jsx, HouseholdSettingsScreen.jsx, InviteMembersScreen.jsx, GroupMembersScreen.jsx.

In plain terms This is the feature that makes everything else in the app make sense — every task, expense, chat, and vault document exists within a household, and this module is what creates that household and controls who's allowed in it. A person can only ever belong to one household at a time — join a new one, and you have to have left the last one first.

Screens

  • HouseholdSetupScreen.jsx — first-run: create a new household or join one with a code.
  • HouseholdSettingsScreen.jsx — name, cover photo, invite code, deletion controls.
  • InviteMembersScreen.jsx — generate/share a one-time invite code or link.
  • GroupMembersScreen.jsx — the member list: roles, remove/promote/transfer actions for admins.

Key rules

  • Creating a household makes you its admin automatically, and every household needs exactly one admin at all times.
  • An admin can't just leave — they have to transfer the admin role to someone else first, so a household is never accidentally leaderless.
  • An admin also can't be removed by another admin (there's only ever one) — the only way to replace an admin is transfer, never forced removal.
  • role exists in two places that are kept in sync: household_members.role (this household specifically) and users.role (a convenience mirror used elsewhere, like JWT payloads) — every role change updates both.
  • Children can't generate invitations — the one place in this module where the child role is specifically blocked from something a regular member can do.

Workflow — Household Deletion

Mirrors the account-deletion pattern in Auth: a 30-day grace period, admin + password confirmed.

schedule-deletion

Admin-only, requires the admin's own account password (skipped only if they're a password-less OAuth account). Sets households.scheduled_deletion_at = now + 30 days and notifies every household member it's happening.

cancel-deletion

Admin-only; clears the timestamp back to null and notifies the household it's been called off.

confirm-deletion

Admin + password again, but this one acts immediately rather than waiting for the 30-day timer: every HouseholdMember row is destroyed (severing everyone's access at once) and the household itself is soft-deleted (paranoid). Tokens

Workflow — Google Calendar Two-Way Sync

Each user who connects gets their own CalendarSyncState row — sync is per-person, not per-household.

In plain terms This only syncs your own Google Calendar to your own connection — if three people in a household all connect Google, each person's created events go to their own calendar, not into some shared Google calendar. An event only ever has one Google-side copy, owned by whoever created it in Rootaroo.
Connect

POST /calendar/google/connect exchanges the mobile app's OAuth authorization code for real Google access/refresh tokens, resolves the user's primary calendar ID, and saves (or refreshes) their CalendarSyncState row — then immediately kicks off a first sync so events show up right away instead of waiting for the next scheduled run.

Pull

syncUserCalendar: fetch Google's changes since the last sync token (Google's own incremental-sync mechanism — not re-downloading everything each time). New/changed events are upserted into CalendarEvent, tagged with their googleEventId; cancelled Google events delete their local counterpart.

Push

Any of the user's own events that were created locally but never made it to Google yet (e.g. created before this connection existed) get pushed out in the same pass.

Scheduling

This whole pull-then-push cycle also runs periodically via a scheduled cron job — not just when the user manually connects — so the two calendars stay roughly in step over time, not just at connection time.
